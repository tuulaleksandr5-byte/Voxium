# Voxel Sandbox 2.0 Survival — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Этапы ниже используют чек-листы для контроля готовности.

**Goal:** Добавить поверх принятой 1.0 Foundation выживание с путём от дерева до алмазных инструментов.

**Architecture:** Детерминированная игровая логика остаётся в независимом от Bevy `game_core`. Ввод и UI отправляют `PlayerAction`, логика проверяет действие и выдаёт события изменения состояния; клиент обновляет мир, HUD, звук и графику по результату. Реестры связывают строковые ID контента с числовыми ID рантайма, а сохранения используют строковые палитры.

**Tech Stack:** Существующие Rust 1.99.1, edition 2024, Bevy 0.20.1 и serde без обновления версий. `ron = "=0.12.3"` уже использовался `game_render`; на этапе 2 он добавлен как прямая зависимость `game_core`. Существующие версии зависимостей не обновлены. `bincode` и `zstd` планируются к этапу 8, их версии определяются после проверки совместимости; сейчас они не добавлены.

**Spec:** [Полное новое ТЗ пользователя](superpowers/specs/2026-11-09-v2-survival.md).

## Общие ограничения

- Исходная 1.0 Foundation принята пользователем: тег `v1.0.0`, исходный коммит `74d34332a587131d3b462c1a99fa21b5769ec13b`. Старые номера пакетов Cargo не меняют этот факт.
- Новое ТЗ определяет **2.0 Survival**; прежняя строка «2.0 — полная прогрессия» в старой дорожной карте больше не задаёт объём этого релиза. Мобы относятся к 3.0, мультиплеер — к 11.0; боссы, машины, авиация и драконы в эту работу не входят.
- Проект расширяется на месте. Bevy и существующие зависимости не обновляются без разрешения пользователя; новые зависимости явно перечисляются в отчёте.
- Высота мира −64…320 включительно, море 63, чанки 16×16, секции 16×16×16. Одна ECS-сущность на обычный блок не создаётся.
- После каждого этапа обязательны сборка, запуск и проверка сохранности старых возможностей. Переход к следующему этапу — после «дальше»; этап 2 уже разрешён этим сообщением пользователя.
- Нет `unsafe`; новые комментарии на русском. Все параметры баланса в RON, ошибки контента в лог без паники.
- Примеры в `assets/data/examples/` — **предложенная схема**, не рабочий каталог и не заявление о реализованных системах. На этапе 2 загружается и обновляется только действующий `assets/data/survival.ron`.
- До завершения всех восьми этапов результат обозначается как альфа 2.0 с указанием завершённого этапа, а не готовая версия 2.0.

## Точки проверки при ревью

1. Повреждённый старый JSON или будущая версия формата не затираются миграцией; проверка контрольной суммы предшествует преобразованию старой схемы.
2. Смена режима, загрузка мира и смерть не оставляют активный полёт, зажатую добычу или повторно применённую команду.
3. Сбой hot-reload оставляет последнюю корректную конфигурацию; изменение баланса руд не меняет генерацию уже созданного мира.
4. Перенос переполненного стека, повторный подбор дропа и закрытие контейнера не дублируют и не теряют предметы.
5. Новые материалы не изменяют 17 исходных PNG, номера слоёв 0…16 и пустой слой 17; старый пользовательский атлас продолжает работать.

## Контракты данных и идентификаторов

`ContentId` — строка вида `namespace:lower_snake_case`. `NumericRegistry` хранит соответствия `ContentId ↔ RuntimeBlockId` и `ContentId ↔ RuntimeItemId`; типы ID блоков и предметов различаются. Число рантайма не является долговременным идентификатором. Неизвестный ID, повтор ID, недопустимый диапазон, отсутствующая ссылка или неверный слой дают ошибку с именем файла и ID записи; новый снимок применяется только после полной проверки.

Начальное сопоставление блоков 1.0:

| Старый ID | Строковый ID | Старый ID | Строковый ID |
|---|---|---|---|
| 0 | `foundation:air` | 8 | `foundation:oak_leaves` |
| 1 | `foundation:grass` | 9 | `foundation:oak_planks` |
| 2 | `foundation:dirt` | 10 | `foundation:cobblestone` |
| 3 | `foundation:stone` | 11 | `foundation:glass` |
| 4 | `foundation:deepslate` | 12 | `foundation:water` |
| 5 | `foundation:sand` | 13 | `foundation:bedrock` |
| 6 | `foundation:gravel` | 14 | `foundation:snow` |
| 7 | `foundation:oak_log` | 15 | `foundation:sandstone` |

Примеры: [блок](../assets/data/examples/blocks.ron), [предметы](../assets/data/examples/items.ron), [руда](../assets/data/examples/ores.ron), [рецепт](../assets/data/examples/recipes.ron), [инструмент](../assets/data/examples/tools.ron). Блоки из таблицы — базовый каталог Foundation, с которым объединяются примеры. `blocks.ron` показывает переопределение одного камня; остальные 15 записей не нужно дублировать ради примера. Запись руды объявляет свой `id` как новый тип рудного блока, а `replaces` ссылается на базовые блоки. `block` у предмета ссылается на базовый либо объявленный рудой блок; все предметные ссылки примеров перечислены в `items.ron`. `tools.ron` задаёт характеристики предмета по совпадающему ID. Новые базовые и глубинные варианты руды сохраняют отдельно свой тип основы; внешний вид выбирает слой 3 или 4 плюс оверлей, а не меняет ID по порядку загрузки.

На этапе 3 загрузчик объединяет каталоги, проверяет блоки/предметы/инструменты/рецепты и затем создаёт `NumericRegistry`. Загрузчики Bevy адаптируют независимые от движка структуры serde; hot-reload повторяет ту же атомарную проверку. Будущий тест `example_catalog_references_resolve` загружает базовые 16 блоков и пять примеров, проверяет все ссылки, wood pickaxe 59/2/0, камень → булыжник и бревно → 4 доски. Он не должен зависеть от случайного порядка чтения файлов.

В будущем `armor.ron` задаёт 4 части и прочность, `enchantments.ron` — эффекты и несовместимости, `experience.ron` — формулы уровней. Примеры этих файлов сейчас не заявлены реализованными.

## Протокол совместимости, согласованный до реализации

1. Определить формат по заголовку, прочитать исходные байты без записи. Для v1 сначала проверить checksum исходного JSON-envelope, затем разобрать **legacy-схему 1**; новая схема не должна добавлять default-поля до проверки checksum.
2. Преобразовать старые `u8` только через неизменную таблицу Foundation выше. Сохранить seed, имя, все правки, позицию, обзор, время; оставить `generator_version = 1`. Не создавать руды в старом мире скрытой перегенерацией.
3. Старому миру назначить **Survival**, свежие здоровье 20, голод 20, начальное насыщение/воздух из действующего RON, истощение 0, XP 0 и пустой количественный инвентарь. Отсутствовавшие в 1.0 статы и вещи нельзя «восстановить» из творческого хотбара. Точку спавна вывести детерминированно из seed; это новый атрибут старого мира, а не замена сохранённой позиции.
4. До первой записи формата 2 создать отдельную резервную копию исходных проверенных байтов, например `<id>.bak_v1`; существующую копию не перезаписывать. Если загрузилась проверенная `.json.bak`, копировать именно её содержимое. Сохранение формата 2 — временный файл → sync → проверка → атомарная замена там, где поддерживается. При ошибке исходник и копия остаются читаемыми.
5. Формат 2 содержит палитры строковых ID для блоков и предметов, версию/снимок генерации, все данные персонажа и блок-сущностей. Числа внутри сжатого чанка ссылаются на его сохранённую палитру; после загрузки преобразуются в текущий `NumericRegistry`.
6. Новые миры с рудами используют генератор 2 и сохранённый снимок параметров руд/их версию. Hot-reload меняет шаблон будущих миров, не этот снимок. Старые миры по генератору 1 продолжают генерироваться точно как 1.0; расширение старого мира рудами потребует отдельного явно реализованного пути.

До этапа 8 не подменять старый JSON несовместимой записью и не обещать полного восстановления новых систем после перезапуска. Временное хранение, если требуется для проверки этапов, должно быть явно отделено от исходного v1 и протестировано на отсутствие потери мира.

## Правила расширения графики

Существующий texture array уже устраняет просачивание соседних тайлов. Слои 0…16 и исходные 17 PNG сохраняются побайтно; слой 17 остаётся пустым. Новый контент начинается с 18, логическая раскладка атласа остаётся 6 колонок с ростом вниз. Старый override-атлас 768×384 дополняется новыми ресурсами без требования перерисовать старые тайлы.

Руды используют отдельный оверлей поверх stone/deepslate, а не 16 полных копий фона. Разрешённые новым ТЗ временные цветные оверлеи имеют пометку `TODO(art)` и используются только для нового контента. Для лавы, огня, глины, обсидиана, верстака, печи, наковальни, сундука, стола, полок и грядки — новые тайлы с той же пометкой; исходные материалы не заменяются заглушками. Предметы получают отдельный атлас 128×128; блоки — изометрическую иконку с более светлой левой и тёмной правой гранью, переиспользуя существующий генератор иконок.

## Команды и критерий проверки каждого этапа

```bash
source /workspace/.voxel-env/activate.sh
cd /workspace/voxel-sandbox-rust
cargo fmt --all -- --check
cargo check --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo run --locked -p voxel-client
```

На обычном компьютере без подготовленной облачной среды строка `source` не нужна. Помимо проверок ядра обязателен фактический запуск с ручным сценарием соответствующего этапа. Отчёт содержит изменённые файлы, новые зависимости, команды, результат проверки, ограничения и следующий этап. Новые короткие файлы примеров можно привести целиком; технический журнал не заменяет проверку игрового сценария.
